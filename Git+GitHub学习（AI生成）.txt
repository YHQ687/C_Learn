一、核心概念：Git 和 GitHub 是什么？
================================================================================

【Git】
  - 是一个安装在本地电脑上的软件。
  - 作用：记录代码版本。项目做到一个阶段，就可以用 Git 把当时的代码保存
    下来，以后改坏了，随时能退回到之前存过的版本。

【GitHub】
  - 是一个网站（云端代码托管平台）。
  - 作用：
      1. 备份代码和版本记录（电脑坏了也不丢）；
      2. 支持多人协作开发；
      3. 可以把项目源码公开，分享给别人。

【一句话区分】
      Git  = 本地软件，负责记录项目的每一次改动（一个本地）；
      GitHub = 远程网站，负责存储代码和 Git 记录（一个远程）。

【为什么 AI 时代更要学？】
      Git 和 GitHub 是写代码必不可少的两样东西，以前是这样，AI 时代
      同样如此。AI 一次改几十个文件很常见，更需要版本管理和远程备份。

================================================================================
二、Git 的安装
================================================================================

--------------------------------------------------------------------------------
方法 1：借助 AI 安装（最简单）
--------------------------------------------------------------------------------
  使用 Codex、Claude Code 等编程 Agent 时，直接告诉 AI "帮我安装 Git"，
  AI 会自动完成整个安装过程。

--------------------------------------------------------------------------------
方法 2：Windows 手动安装
--------------------------------------------------------------------------------
  1. 打开 Git 官网下载页，点击 "Install for Windows"，
     再点击 "Click here to download" 下载安装包。
  2. 打开安装包，像装普通软件一样，一路点击 Next。
  3. 取消勾选 "View release notes"（发布记录，没什么用），点完成。
  4. 验证：开始菜单搜索并打开 "Git Bash"，输入：

            git --version

     若显示 Git 版本号，说明安装成功。

--------------------------------------------------------------------------------
方法 3：MacOS 手动安装
--------------------------------------------------------------------------------
  1. 打开"终端"，输入：

            git --version

  2. 情况 A：直接显示版本号 → 已经装好了（Git 很常用，可能在装其他软件
     时被顺带安装了）。
  3. 情况 B：提示需要安装 Xcode 命令行开发者工具（Dock 栏会出现图标，
     弹窗提示）→ 点击"安装"，同意协议，等待安装完成。
       说明：命令行开发者工具是苹果的一整套开发工具，除了 Git，还包含
       编译器、调试工具等，开发必备，早晚要装，建议直接装全套。
  4. 安装完成后再次执行 git --version，能看到版本号即成功。

================================================================================
三、让 Git 开始管理项目
================================================================================

【示例项目】马克待办（一个简单的待办软件），文件夹里有两个文件：
      index.html  —— 待办软件的页面代码（约 100 多行）；
      readme.md   —— 项目说明文件（写项目是做什么的、怎么用），还没写完。
  这两个文件扩展名不同，但本质都是普通文本文件，都可以用文本编辑器
  （如 VS Code）打开和修改。

--------------------------------------------------------------------------------
1. 进入项目目录：cd
--------------------------------------------------------------------------------
      cd 项目文件夹路径
  例： cd ~/Desktop/马克待办        （进入桌面上的马克待办文件夹）
  说明：cd 不是 Git 命令，是终端命令（change directory），但使用频率
  极高，必须记住。

--------------------------------------------------------------------------------
2. 初始化仓库：git init（第一个 Git 命令）
--------------------------------------------------------------------------------
      git init
  作用：把当前目录初始化成一个 Git 仓库，从此项目具备版本管理能力。
  本质：在当前目录下创建一个隐藏的 .git 文件夹，以后所有跟 Git 相关的
       东西（包括保存的版本）都存在这里。
  注意：
    - "空仓库"指里面还没保存任何版本，不代表 .git 文件夹是空的，
      初始化时 Git 已经在里面准备了一些文件（不用关心它们是干什么的）。
    - .git 文件夹默认隐藏，Mac 上可按快捷键显示/隐藏隐藏文件，平时
      保持隐藏即可，避免文件列表显得乱。

--------------------------------------------------------------------------------
3. 查看仓库状态：git status（非常常用）
--------------------------------------------------------------------------------
      git status
  作用：查看当前 Git 仓库的状态。
  初始化后会提示有 "Untracked files"（未跟踪的文件），即 readme.md 和
  index.html：Git 已经发现了这两个文件，但还没开始跟踪它们的内容，也没
  把它们存成版本。
  （输出里还有 branch、commit 等词，初学暂时不用深究。）

================================================================================
四、三大区域与保存版本的原理（重点理解）
================================================================================

项目目录里的东西分为两类、共三个区域：

  1. 工作区（Working Directory / Working Tree）
       —— 我们自己的项目文件，即 index.html、readme.md 等。
       注意：工作区英文有两种说法，working directory 和 working tree，
            都是一个意思，不必纠结。

  2. 暂存区（Staging Area / Index）
       —— 在 .git 文件夹内，临时存放"下一次准备提交"的改动。

  3. 提交历史（Commit History）
       —— 在 .git 文件夹内，存储所有已生成的 commit 版本。

【保存一个版本 = 两步】

  第一步：git add（把文件从工作区放进暂存区）
       把要保存的文件内容复制一份放到暂存区；不想保存的文件不放进去。

  第二步：git commit（把暂存区内容打包成版本，存入提交历史）
       把暂存区里的所有内容打包，生成一个版本（叫 commit），
       放到提交历史里。
       commit 就是"版本"，翻译过来是"提交"；提交历史也叫 commit 历史。

【为什么要有暂存区？（暂存区的意义）】
       暂存区让我们可以一点一点"挑出"下一次要提交的内容。
       比如重构后多出很多文件、已有文件也改了，可以慢慢挑选：先挑
       index.html，再挑对应的 JS、CSS 文件（git add 支持一次添加多个
       文件），全部挑好、确认暂存区内容无误后，再统一 commit。

================================================================================
五、实际操作：完整的提交流程
================================================================================

--------------------------------------------------------------------------------
第 1 步：把文件加入暂存区
--------------------------------------------------------------------------------
      git add index.html          （添加单个文件）
      git add 文件1 文件2          （一次添加多个文件）
      git add .                   （添加当前目录所有改动，最常用）
  执行后再用 git status 查看：
       "Changes to be committed"（准备提交的改动）下面列出的文件，
       表示已经进入暂存区，等着被提交为 commit。
       没被 add 的文件仍在 "Untracked files" 里。

--------------------------------------------------------------------------------
第 2 步：首次使用前，配置提交人姓名和邮箱（只需一次）
--------------------------------------------------------------------------------
      git config --global user.name "你的名字"
      git config --global user.email "你的邮箱"
  说明：
    - 每个 commit 都会记录提交人的名字和邮箱，所以要提前告诉 Git。
    - 这两条命令只需设置一次，这台电脑上所有项目通用，不用重复设置。
    - 这不是登录账号，Git 不会做校验，找个合适的名字和邮箱填上即可。

--------------------------------------------------------------------------------
第 3 步：提交版本
--------------------------------------------------------------------------------
      git commit -m "提交说明"
  例： git commit -m "添加待办页面"
  说明：
    - -m 是 message 的意思，给这次提交附上一段说明。
    - 一个项目可能有几十上百个 commit，写清楚每个 commit 做了什么，
      以后回头看历史时能很快知道每次修改的内容。

--------------------------------------------------------------------------------
第 4 步：查看提交历史
--------------------------------------------------------------------------------
      git log                 （查看完整 commit 历史）
      git log --oneline       （每个 commit 只占一行，简洁显示）
  每条记录包含：
    - 一长串字母数字：commit 的唯一编号（像身份证号，不会重复）；
    - 提交人名字和邮箱；
    - 提交时间；
    - 提交说明（-m 后面写的内容）。
  --oneline 只显示编号前几位和提交说明，commit 多时更清楚。
  退出历史界面：按 Q。

  提交后再执行 git status：
    - 已提交的文件不再出现在改动列表里（不是文件不见了，而是它的内容
      与最新 commit 一致，没有新改动需要提示）；
    - 没被 add 的文件（如 readme.md）仍在 Untracked files 里。

【日常开发的固定流程】
      每完成一个阶段性工作，就重复：git add → git commit，
      把每个阶段成果记录下来，整个项目历史就被完整保存，回溯、回滚
      都有据可查，再也不怕改坏项目。

================================================================================
六、代码回滚（三种场景）
================================================================================

回滚方法取决于"改动走到了哪一步"，一共有三种情况。
（以把 index.html 改成深色主题、后来又想撤销为例。）

--------------------------------------------------------------------------------
场景 1：改动只在工作区（改完文件，没做任何 Git 操作）
--------------------------------------------------------------------------------
  确认状态：git status 会在文件前标 "modified"，并提示
           "Changes not staged for commit"（改动还没进暂存区）。
  查看具体改了什么：git diff
       前面减号（-）表示删除的行，加号（+）表示新增的行；
       J/K 逐行上下移动，F/B 整页上下翻，Q 退出。

  回滚命令：
       git restore 文件名        （撤销单个文件的工作区改动）
       git restore 文件1 文件2    （同时撤销多个文件）
       git restore .            （撤销当前目录所有改动，最常用）

  说明：
    - git restore 用于撤销工作区的改动，恢复到上一次提交的状态。
    - 点（.）代表当前目录。AI 一次改几十个文件时，用 git restore .
      把所有改动一起回滚，最常用。
  验证：git status 显示 "nothing to commit, working tree clean"
       （没有需要提交的内容，工作区干净），页面也恢复原样。

--------------------------------------------------------------------------------
场景 2：改动已进入暂存区（执行了 git add，但还没 commit）
--------------------------------------------------------------------------------
  需要分两步：先把改动从暂存区撤回到工作区，再从工作区撤销。

  第一步（撤出暂存区）：
       git restore --staged 文件名
       git restore --staged .          （撤出当前目录所有文件，常用）

  第二步（撤销工作区改动）：
       git restore .

  关键点：
    - --staged 命令只修改 Git 的数据，把改动从暂存区移回工作区，
      文件本身内容一点没变（页面还是深色主题）。
    - 执行完第一步，git status 会变回 "Changes not staged for commit"，
      说明改动只在工作区了；再执行 git restore . 才真正撤销文件内容。

--------------------------------------------------------------------------------
场景 3：改动已提交为 commit（执行了 git add 和 git commit）
--------------------------------------------------------------------------------
  先理解 HEAD：
    - HEAD 指向提交历史里最新的那个 commit（git log 里会标出来）。
    - HEAD~1 = 上一个 commit（倒数第二个）；
      HEAD~2 = 上上个 commit（倒数第一个），以此类推。
    - HEAD 会随新提交不断移动：每提交一个新 commit，HEAD 就挪到最新的
      commit 上，HEAD~1、HEAD~2 也依次移动。

  回滚命令（git reset）：
       git reset --hard HEAD~1
  含义：
    - reset 是"重置"，让 HEAD 移动到 HEAD~1（倒数第二个 commit），
      原来最新的那个 commit 就被删掉、没人管了。
    - --hard 表示三个区域（工作区、暂存区、提交历史）一起回滚，全部
      恢复成 HEAD~1 的样子，深色主题改动从三个区域彻底消失。

  验证：git log 里最新的错误 commit 消失（3 条变 2 条）；
       git status 显示 working tree clean；页面恢复浅色。

  【重要警告】--hard 非常彻底，会把工作区、暂存区里所有未提交的改动
  一起清掉。执行前最好先 git status 看一眼，确认没有需要保留的改动。

--------------------------------------------------------------------------------
git reset 的三种模式（区别在于回滚影响哪些区域）
--------------------------------------------------------------------------------
  三个区域：工作区、暂存区、提交历史。

    --hard   ：三个区域全部回滚（最彻底）。
    --mixed  ：只回滚暂存区和提交历史，改动保留在工作区。
               这是默认模式，即 git reset HEAD~1 不写选项时等同于 --mixed。
    --soft   ：只回滚提交历史，工作区和暂存区的改动都保留。

  使用场景：
    - commit 后发现小问题、想改完再重新提交 → 用 --mixed 或 --soft，
      commit 被撤掉但改动还在，接着改、改完再提交。
    - 就是不想要这个改动、想让它彻底消失 → 用 --hard。

--------------------------------------------------------------------------------
另一种回滚方式：git revert（通过"新增"一个回滚 commit 来撤销）
--------------------------------------------------------------------------------
  原理：不是删除原来的 commit，而是让 Git 自动把代码"反着改回来"
       （之前加的行现在删掉，之前把 ABC 改成 XYZ，现在改回 ABC），
       再把这个反向改动提交成一个新 commit，用新 commit 抵消旧 commit。

  命令：
       git revert HEAD
  说明：
    - 创建一个新 commit，其改动与最新 commit 正好相反，用来抵消它。
    - 执行后会进入一个编辑界面（Vim），显示新 commit 的说明：
      第一行写 "Revert ..."（回滚了哪个 commit），
      下面一行写出被回滚的 commit id，非常精确；
      以 # 开头的是注释，会被忽略。
    - 新手建议直接保存退出，使用默认信息即可（默认信息已经准确）。
    - Vim 保存退出：输入  :wq  再回车。

  优点：
    - 原来的错误 commit 仍保留在历史里，git log 里会多出一个反向的新
      commit；哪天又后悔了，还能从历史里找回原来的改动，整个过程可追溯。

  【两种回滚方式对比】
    git reset  ：删除 commit、让 HEAD 后退（历史被改写，--hard 很彻底）；
    git revert ：新增反向 commit 来抵消（历史完整保留，可追溯）。

================================================================================
七、.gitignore：让 Git 忽略指定文件
================================================================================

【问题】不是项目里的所有文件都要被 Git 记录。比如学习时随手建的
notes.txt（个人学习笔记），和项目功能无关，不想提交，也不想让它总在
git status 里出现。

【解决】在项目根目录新建一个文件，名字就叫 .gitignore，把不想让 Git
跟踪的文件名写进去，这些文件就会被 Git 忽略。

  例：.gitignore 内容
       notes.txt
       .DS_Store

  说明：
    - 写入后再执行 git status，notes.txt 就从未跟踪列表里消失了，
      说明已被忽略。
    - 文件本身不会被删除，本地依然存在，可以继续打开编辑，只是 Git
      不再提示它。
    - 可以写很多个文件/规则。比如 .DS_Store 是 Mac 上自动生成的隐藏
      文件（调整文件夹视图时会产生），和代码无关，可提前忽略。

【.gitignore 本身要提交】
    .gitignore 是项目的一部分，需要用 git add、git commit 提交。
    提交后规则会随项目一起保存，换一台电脑做这个项目时规则还在，
    不用重新写。

================================================================================
八、分支（Branch）
================================================================================

--------------------------------------------------------------------------------
1. 分支是什么？
--------------------------------------------------------------------------------
  git log 里最新 commit 旁边除了 HEAD，还有一个名字（master 或 main），
  这就是分支名。
  本质：分支是一个"贴在 commit 上的可移动标签"。
       每提交一个新 commit，这个标签就跟着挪到最新 commit 上；
       从分支标签往回找，能找到的这一串 commit，就是这个分支的历史。

  主分支：master 或 main（不同环境默认名不同，不用纠结）。
       它是项目的主分支，一般要求上面的代码始终保持稳定、可以正常使用，
       不要长期放一堆做了一半、不能用的功能。

【为什么需要分支？】
  假设要开发"截止时间"新功能，可能要拆成 3 个 commit：
    ① 做截止时间界面；② 写保存逻辑；③ 过期判断与提醒。
  如果直接在 master 上提交：
    - 提交第 1 个 commit 后，保存逻辑还没写，master 代码处于半可用状态，
      用户一点相关按钮产品就可能报错；
    - 中间没完成的 commit 都进入主分支，master 会在一段时间内不稳定。
  正确做法：
    - 基于稳定的 master 创建一个新分支，专门开发这个功能，相关 commit
      都先提交到新分支，开发期间 master 始终保持稳定；
    - 新功能全部完成、测试通过后，再把新分支合并回 master
      （合并本质是把 master 标签挪到与新分支相同的位置）。

--------------------------------------------------------------------------------
2. 分支的创建、查看、切换
--------------------------------------------------------------------------------
  创建分支：
       git branch 分支名
  例： git branch feature/due-date
       （feature 表示"功能"，due-date 是"截止时间"；很多团队习惯用
        feature/ 开头表示新开发的功能。分支名可带斜杠，Git 对分支名
        限制不严格，叫 new-date 甚至 abc 都可以。）

  查看所有分支：
       git branch
       会列出所有分支，当前所在分支前面有星号（*）。
       注意：创建分支和切换分支是两件事，git branch 只创建、不会切过去。

  切换分支：
       git switch 分支名

  创建并立即切换（最常用，推荐）：
       git switch -c 分支名
       （-c 是 create，先创建分支再立刻切过去，等于把上面两条合一。）

  老写法（了解即可）：
       git checkout -b 分支名
       效果和 git switch -c 完全一样；checkout 是更老的写法，功能太多
       （除了切分支还能干别的），新手容易混淆，所以后来 Git 把切换分支
       单独拆成了 git switch。自己用推荐 git switch -c。

  提示：刚创建并切换到新分支时，项目目录看起来没有任何变化（文件、内容
       都一样），因为新分支是从 master 最新 commit 叉出来的，此刻两条
       分支指向同一个 commit；真正的区别要等在新分支提交新 commit 后才
       显现。

--------------------------------------------------------------------------------
3. 在新分支上开发
--------------------------------------------------------------------------------
  切到新分支后正常开发、提交（git add → git commit），每个 commit 都
  属于当前分支。
  开发完成后用 git log --oneline 查看：
    - 新分支标签指向最新的功能 commit，master 标签还停在原来的 commit；
    - 新分支比 master 多出的几个 commit 只属于新分支。
  切回 master 验证：
    - git log 里看不到新分支的 commit，页面里也没有新功能，
    - 说明新分支上的改动完全没有影响 master。

--------------------------------------------------------------------------------
4. 合并分支：git merge
--------------------------------------------------------------------------------
  先想清楚：合并是"把别的分支合并到你当前所在的分支上"。
  想把 feature/due-date 合到 master，就必须先切到 master，再合并。

       git switch master                 （先切到 master，确认星号在 master）
       git merge feature/due-date       （把功能分支合并到当前分支）

  合并后：
    - 新功能出现在 master 上，新分支的 commit 全部进入 master 历史；
    - master 和功能分支标签指向同一个 commit，代码完全一样。

  删除已合并、不再需要的分支：
       git branch -d 分支名
       （-d 是 delete；功能合并后该分支就没用了，可删除。）

================================================================================
九、合并冲突（Conflict）
================================================================================

【场景搭建】手上有两个新功能，各自一个分支（都从 master 拉出）：
    排序功能（feature/sort）：点一下按截止时间排序，分 3 个 commit；
    全部完成（feature/complete-all）：点一下把所有待办标记完成，分 3 个
    commit。

【合并过程】
    先切回 master，git merge 排序分支 → 顺利合并。
    再 git merge 全部完成分支 → 出问题！
    输出里出现大写 "CONFLICT"，最后提示
    "Automatic merge failed"（自动合并失败），这就是冲突。

【为什么冲突？】
    - 排序分支合并后，master 在"添加"按钮下面加了一行"排序"按钮；
    - 全部完成分支是在排序之前就从 master 叉出去的，它也要在"添加"按钮
      下面插一行，不过是"全部完成"按钮。
    - 两条分支都想在同一个位置插入不同内容，Git 无法判断最终保留哪个、
      谁先谁后，只能停下来让人手动处理。

【解决冲突的步骤】
  1. 先 git status：会出现 "Unmerged paths"（未合并完成的文件），
     冲突文件标 "both modified"（两边都改过）。
     提示：解决冲突后执行 git commit；
          不想合并可执行 git merge --abort 放弃这次合并。

  2. 打开冲突文件（如 index.html，用 Vim 或 VS Code），里面有 Git 写入
     的冲突标记，把代码分成上下两部分：

          <<<<<<< HEAD
          （当前分支 master 的代码，这里是"排序"按钮）
          =======
          （要合并进来的分支 feature/complete-all 的代码，这里是"全部完成"按钮）
          >>>>>>> feature/complete-all

  3. 手动编辑：删除这三行标记符号（<<<<<<<、=======、>>>>>>>），把代码
     改成最终想要的样子。本例两个按钮都要，就把两个按钮都留下、只删标记。

  4. 保存后，把改动加入暂存区并提交：
          git add .
          git commit
     （注意：冲突解决后必须再 commit，这次合并才算完成。）

  5. 验证：git status 显示 working tree clean；页面上两个按钮都出现，
     合并成功。

【快进合并（fast forward）】
    - 第一次合并排序分支时，排序分支是从 master 当前 commit 直接往后延伸
      的，master 有的它全有，只是多了几个 commit；这时 master 直接"快进"
      挪到排序分支位置即可，不产生新 commit，也不用手动 commit。
    - 第二次合并时，master 已经挪到排序分支，而全部完成分支是从旧位置
      岔出去的、没有排序的 commit，不能快进（否则排序功能会丢）；Git 会
      新造一个同时接在两边最新 commit 之后的"合并 commit"，把两个分支
      代码合起来，master 再挪到这个新 commit。
    - 没有冲突时这个合并 commit 由 Git 自动提交；有冲突时 Git 停下来，
      手动解决后再自己 git commit —— 这就是第二次合并多一步的原因。

================================================================================
十、Rebase（变基）：让冲突尽早暴露
================================================================================

【问题】冲突往往在最后合并的那一刻才爆出。小功能冲突少还好；真实开发中
一个功能做一两周、几十个 commit，期间 master 也在不停更新，等到最后才
合并，可能有很多冲突，甚至发现自己的实现和 master 根本不兼容、要返工。

【思路】开发过程中，时不时把自己的分支"挪到 master 最新位置后面"：
    - 别人的新代码能及时拿到；
    - 挪的时候若改了同一处就会冲突，但此时改动少，当场就能解决；
    - 能提前感知与 master 不兼容的问题，不用等到最后。
    - 等功能做完，由于分支一直跟在 master 最新后面，最后合并就是一次
      快进，冲突早就在前面一次次解决掉了。

【什么是 rebase】
    rebase = re（重新）+ base（地基，即分支岔出去的那个 commit）。
    就是给分支重新换一个地基：把分支从旧的岔出点，挪到 master 最新
    commit 的后面。

【命令与流程】
    （在自己的功能分支上）
       git rebase master

  实际执行细节：
    - rebase 不是把整条分支一下子搬过去，而是把分支上的 commit 一个个
      "在新地基里重新做一遍"。
    - 过程中某个 commit 出现冲突时会停下来报错（无法应用该 commit）。

  解决冲突：
    1. 打开冲突文件，冲突标记含义和之前一样，删掉标记、改成最终内容；
    2. 暂存改动：   git add .
    3. 注意：这里不是 git commit，而是继续变基：
                git rebase --continue
       之后 Git 会弹出该 commit 原来的提交说明，不用改，保存退出即可；
       Git 会继续搬剩下的 commit，全部完成后提示 "Successfully rebase"。

  完成后：
    - 功能分支已经接在最新 master 后面，可继续开发；
    - 功能做完后切到 master 再 git merge，此时是 fast forward 快进，
      只需把 master 挪到功能分支位置，不产生新 commit。

十一、Stash：临时存起没写完的代码
================================================================================

【场景】正在开发"清空已完成"功能，第二个 commit 的函数才写一半，突然
有用户反馈一个线上 bug（完成待办后日期被错误地划了删除线），需要赶紧切
回 master 修复。
    但切分支时 Git 提示：本地未提交的改动会被覆盖，切换失败
    （写了一半的代码会丢失）。报错给两条路：
      commit your changes（提交，但函数没写完，提交半成品不合适）；
      stash them（暂存，即本节主角）。

【stash 是什么】
    stash 意思是"藏起来、存起来"。.git 里除了暂存区、提交历史，还有一块
专门收东西的地方叫 stash。
    执行 git stash 后，工作区（以及暂存区）里所有未提交的改动都会被整个
挪到 stash 里，工作区恢复到上一次提交时的干净状态，这时就能顺利切分支；
忙完别的，再把改动从 stash 取回工作区，接着写。

【命令】
       git stash              （把所有未提交的改动存起来，工作区变干净）
       git stash pop          （把 stash 里的改动取回工作区）

  执行 git stash 后：
    - 输出里的 "index" 指暂存区（暂存区也叫 staging area 或 index），
      说明 stash 同时处理工作区和暂存区 —— 只要还没提交成 commit 的改动
      都会被收走；
    - "WIP" 是 Work In Progress（正在做的活），指未提交的改动；
    - git status 显示 working tree clean，编辑器里写了一半的代码也消失
      了，回到上一次提交的样子。

  规范地修 bug（不要直接在 master 上改）：
    - 从 master 拉一条 hotfix（紧急修复）分支，在上面修复，测试通过后
      合回 master，再删除 hotfix 分支；
    - （hotfix 和 feature 一样是命名习惯，表示这条分支用来修 bug。）

  取回改动：
    - 切回原来的功能分支，执行 git stash pop，半成品代码回到工作区；
    - 可用 git diff 验证（写了一半的函数又回来了，状态和存起来前一样），
      然后继续开发。

【适用场景】临时被打断、先去干别的、很快就回来 —— stash 很合适。

================================================================================
十二、Git Worktree：多工作区并行开发
================================================================================

【stash 的局限】同时开发多个分支时，要在分支间来回写，就得频繁地
git stash、git stash pop，非常麻烦。根源是只有一个项目目录，同一时刻
里面只能放一条分支的代码。

【思路】再开一个目录：原目录里写一半的代码原样保留，到新目录里做别的
事情，两个目录互不干扰。

【worktree 的核心结构（重点）】
    - 一个工作区 + 它自己的暂存区 = 一个 worktree；
    - 每个 worktree 都有自己独立的工作区和暂存区，互不干扰；
    - 但是所有 worktree 共用同一份提交历史（commit 历史只有一份）。
    无论在哪个 worktree 提交，commit 都记到同一份历史里，另一边马上
    能看到。

【命令】
  新建 worktree：
       git worktree add ../新目录名 -b 新分支名 基于的分支
  例（在原项目目录里执行）：
       git worktree add ../马克待办统计 -b feature/stats master
  含义：
    - git worktree add：创建一个 worktree；
    - 需要指定两件事：① 对应哪个分支；② 放在哪个目录；
    - -b feature/stats master：基于 master 创建并切换到 feature/stats
      分支，这个 worktree 负责该分支的代码；
    - ../马克待办统计：在父级目录（..）下创建"马克待办统计"文件夹，
      worktree 代码放在里面。

  查看所有 worktree：
       git worktree list
       每行显示目录和对应分支；注意原来的目录本身也是一个 worktree
       （从一开始就在用，只是之前只有一个）。
     提示：Git 默认可能把中文路径转成八进制编码显示（历史遗留问题），
          配置禁止转义后再 list 即可正常显示。

  在新 worktree 里开发：
    - 打开新目录里的文件修改，cd 到新目录后正常 git add、git commit；
    - git branch 里，在其他 worktree 中打开的分支前面会标加号（+），
      星号（*）表示当前所在分支。

  合并与清理：
    - worktree 里建的分支是普通分支，合并方法和之前一样：切到 master，
      git merge，再删除分支；
    - 删除 worktree（不要直接在访达/文件管理器里把文件夹扔进废纸篓，
      那样只删了文件，Git 里的记录还在，会出问题）：

          先 cd 回到原目录（别停在待删目录里），再执行：
          git worktree remove 目录名
       这会把文件夹和对应的 Git 记录一起删除；git worktree list 会只剩
       原来的一个，文件夹也一并消失。

【worktree vs 直接复制文件夹（最大区别）】
    - worktree 与原目录共用同一个仓库、同一份提交历史：在新目录里提交、
      合并的 commit，即使新目录被删了，在原目录里依然能看到、能找到，
      代码不会丢；
    - 直接复制粘贴文件夹得到的是两个各自独立的仓库，在一边提交，另一边
      完全不知道。

【适用场景】同时并行开发多个功能，不用频繁 stash，不同分支的开发环境
互不干扰。

================================================================================
十三、GitHub 远程操作
================================================================================

--------------------------------------------------------------------------------
准备：注册账号
--------------------------------------------------------------------------------
  去 GitHub 官网注册一个账号（仓库名不能用中文，中文名可写在描述里）。

--------------------------------------------------------------------------------
1. 配置身份验证：SSH Key
--------------------------------------------------------------------------------
  背景：GitHub 已不支持账号密码验证，现在常用 SSH Key（可理解为密码的
  替代品，但它是两个文件：私钥 + 公钥）。

  原理：
    - 在本地生成私钥和公钥两个文件：
        私钥：留在本地，绝对不能公开、不能发给任何人；
        公钥：发给 GitHub 一份，可以公开。
    - 每次推代码时，本地用私钥生成一个特殊标记（"签名"，只有你的私钥
      做得出、别人仿不了，像亲笔签名），随代码一起发过去；
    - GitHub 用你之前给的公钥检查签名：公钥能认出这个签名是不是配对的
      私钥做的，对得上就确认是你本人推的代码。

  第 1 步：生成密钥对
       ssh-keygen -t ed25519 -C "你的邮箱"
       （ssh-keygen 是生成 SSH key 的命令，gen = generate；
        -t ed25519 指定 key 类型，是 GitHub 推荐类型，照写即可；
        -C 后面是备注，一般写自己的邮箱，方便辨认这个 key 是谁的。）
    回车后会问几个问题：
      - 文件保存位置：默认在用户目录 ~/.ssh/id_ed25519，直接回车用默认；
      - 是否给私钥设密码：设了更安全但更麻烦，个人电脑可直接回车跳过，
        再回车确认一次。
    生成后：id_ed5519 是私钥，id_ed25519.pub 是公钥（.pub = public）。

  第 2 步：查看并复制公钥内容
       cat ~/.ssh/id_ed25519.pub
       （cat 把文件内容显示出来，复制输出的公钥内容。）

  第 3 步：把公钥添加到 GitHub
       右上角头像 → Settings → 左侧 "SSH and GPG keys"
       → New SSH key → 把公钥内容粘贴到文本框 → Add SSH key。

  第 4 步：测试连接
       ssh -T git@github.com
       第一次连接可能提示无法确认 github.com 身份、问是否继续，输入
       yes 回车；之后出现成功提示，说明 SSH key 配置完成。

--------------------------------------------------------------------------------
2. 在 GitHub 上创建空仓库
--------------------------------------------------------------------------------
  头像 → Your repositories → 右上角 New：
    - Repository name：仓库名（如 mark-todo，不能用中文）；
    - Description：描述（中文名可写在这里，如"马克待办"）；
    - Choose visibility：默认 Public（公开），不想公开可选 Private（私有，
      只有自己能看）；
    - 下面三个选项 Add README、Add .gitignore、Add license 都不勾选
      （目标是把本地已有代码推上去，不需要 GitHub 额外加文件）；
    - 点 Create repository，得到一个空仓库。

  页面会提示 "Push an existing repository from the command line"
  （从命令行推送已有仓库），下面给出命令。

--------------------------------------------------------------------------------
3. 把本地代码推送到 GitHub
--------------------------------------------------------------------------------
  第 1 条：关联远程仓库并命名为 origin
       git remote add origin 仓库地址
       （让 Git 记住 GitHub 仓库地址，并给它起个别名 origin；以后说
        origin 就指这个 GitHub 仓库，不用每次写完整地址。origin 只是
        习惯命名，取别的名字也可以。）

  第 2 条（改主分支名）：不需要执行
       那条命令是把主分支从 master 改成 main；我们用 master 即可，跳过。

  第 3 条：首次推送
       git push -u origin master
       （把本地 master 分支和所有 commit 推送到 origin 仓库；
        -u 把本地 master 与远程 master 绑定，绑定后以后直接 git push
        即可，不用再写完整命令。）
     注意：GitHub 给的模板里可能写的是 main，要根据自己的实际主分支名
          改成 master。

  推送成功后回到 GitHub 刷新：
    - 页面变成项目样子，能看到项目文件，README 会自动展示在仓库首页
      （所以大家都用 README 介绍项目）；
    - 推送上去的不只是当前文件，而是整个 Git 仓库的历史（所有 commit
      都在，和 git log 里看到的一模一样）。

--------------------------------------------------------------------------------
4. 日常使用流程
--------------------------------------------------------------------------------
  本地照常开发，改完代码后执行三条命令：
       git add .
       git commit -m "提交说明"
       git push                  （首次绑定后，直接 git push 即可）

  git status 中的提示：
    - 本地比远程多了还没推送的 commit 时，会提示
      "Your branch is ahead of 'origin/master' by N commit(s)"，
      用 git push 推上去；
    - 推送后显示 "Your branch is up to date with 'origin/master'"，
      表示本地和远程代码完全一致。

  这样既保证 Git 里有完整开发历史，又保证 GitHub 上始终有最新备份。

--------------------------------------------------------------------------------
5. 克隆恢复：git clone（验证备份有效性）
--------------------------------------------------------------------------------
  模拟项目文件夹被误删、本地代码和提交记录全部丢失，从 GitHub 恢复：

  1. 到 GitHub 仓库页面，点 Code，确认选 "SSH"，点复制按钮复制仓库地址；
  2. 终端进入想存放项目的位置（如桌面），执行：

       git clone 仓库地址 本地文件夹名
  例： git clone git@github.com:用户名/mark-todo.git 马克待办
       （把 GitHub 上的仓库拉到本地；拉取后文件夹名为"马克待办"，
        而不是默认的 mark-todo。）
  3. 进入文件夹可以看到：所有提交记录都回来了，页面也和之前一模一样，
     备份恢复成功。

十四、常用命令速查表
================================================================================

【安装与配置】
  git --version                          查看 Git 版本（验证安装）
  git config --global user.name "名字"    配置提交人姓名（仅一次）
  git config --global user.email "邮箱"   配置提交人邮箱（仅一次）

【仓库基础】
  cd 路径                                进入目录
  git init                               初始化 Git 仓库
  git status                             查看仓库状态
  git diff                               查看工作区具体改动

【提交版本】
  git add 文件名                         添加指定文件到暂存区
  git add .                              添加当前目录所有改动到暂存区
  git commit -m "说明"                   提交暂存区为一个 commit
  git log                                查看完整提交历史
  git log --oneline                      单行简洁查看提交历史

【回滚】
  git restore 文件名                     撤销工作区指定文件改动
  git restore .                          撤销当前目录所有工作区改动
  git restore --staged 文件名            把指定文件撤出暂存区
  git restore --staged .                 把当前目录所有改动撤出暂存区
  git reset --hard HEAD~1                三区域一起回滚（删除最新 commit）
  git reset --mixed HEAD~1              回滚历史和暂存区，改动留工作区（默认）
  git reset --soft HEAD~1               只回滚历史，改动留工作区和暂存区
  git revert HEAD                        新增反向 commit 抵消最新 commit

【忽略文件】
  （在项目根目录新建 .gitignore，写入要忽略的文件名；.gitignore 本身要提交）

【分支】
  git branch                            查看所有分支
  git branch 分支名                      创建分支
  git switch 分支名                      切换分支
  git switch -c 分支名                   创建并切换分支（推荐）
  git checkout -b 分支名                 创建并切换分支（老写法，了解即可）
  git merge 分支名                       把指定分支合并到当前分支
  git branch -d 分支名                   删除分支
  git merge --abort                      放弃本次合并

【Rebase 变基】
  git rebase master                      把当前分支变基到 master 最新位置
  git rebase --continue                  解决冲突后继续变基

【Stash 暂存】
  git stash                             存起所有未提交改动，工作区变干净
  git stash pop                         取回暂存的改动

【Worktree 多工作区】
  git worktree add 路径 -b 分支名 基础分支   新建 worktree
  git worktree list                      查看所有 worktree
  git worktree remove 目录名             删除 worktree（连同 Git 记录）

【GitHub 远程】
  ssh-keygen -t ed25519 -C "邮箱"        生成 SSH 密钥对
  cat ~/.ssh/id_ed25519.pub             查看公钥内容
  ssh -T git@github.com                 测试与 GitHub 的连接
  git remote add origin 仓库地址         关联远程仓库并命名 origin
  git push -u origin master             首次推送并绑定 master 分支
  git push                              日常推送（绑定后直接用）
  git clone 仓库地址 本地文件夹名         克隆远程仓库到本地

十五、整体知识脉络（复习主线）
================================================================================

  安装 Git  →  git init 让 Git 管理项目
            →  理解三大区域：工作区 → 暂存区 → 提交历史

            →  worktree：多个独立工作区并行开发，共用一份历史
            →  GitHub：配置 SSH → 建仓库 → push 推送 → clone 恢复
